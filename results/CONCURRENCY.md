# 并发评测干扰实测（2026-11-03，本 x86_64 服务器）

机器：KVM 虚拟机，AMD EPYC 7K62，16 物理核 × 2 SMT，4 个 L3 域（每域 4 核 / 16 MiB），62 GiB，无 swap。

方法：`./bench interference`。用指数传播的冻结参考实现（KIOPS）作为提交重复评测，每次 69 次验解全部通过，并按已激活 baseline 计分。环境完全无干扰时得分恰为 50.0（时间比 R = 1，score = 100 / (1 + R)）。得分每降低 1 分约相当于计时变慢 4%。开发负载为 9 个开发 slot 同时运行内存带宽压力程序（64 MiB 数组反复复制），代表 agent 群体可能产生的最坏情况。原始记录见 `store/interference/*.json`。

| 布局 | 并发评测 | 开发负载 | 各 slot 得分 | one-shot / reuse 中位时间比 |
| --- | --- | --- | --- | --- |
| packed（评测核同在一个 L3 域） | 1 | 无 | 50.01 | 0.998 / 0.999 |
| packed | 2 | 无 | 49.23、48.92 | 1.02–1.06 / 1.02 |
| packed | 4 | 无 | 37.54、44.77、45.71、44.63 | 1.13–1.40 / 1.13–1.57 |
| packed | 1 | 9 slot | 49.00 | 1.07 / 1.03 |
| packed | 4 | 9 slot | 41.12、39.75、35.58、38.87 | 1.37–1.88 / 1.34–1.75 |
| spread（每个 L3 域一个评测核） | 1 | 无 | 49.25 | 1.02 / 1.02 |
| spread | 4 | 无 | 43.61、41.87、39.50、42.12 | 1.10–1.42 / 1.27–1.78 |

结论：

1. 单独评测能复现 baseline（50.01），隔离和计时路径本身是可信的。
2. 评测之间的相互干扰远大于开发负载的影响：4 个并发评测让计时变慢 13–88%。把评测核分散到不同 L3 域并没有改善，说明瓶颈不在缓存。4 个并发时，评测专用 Docker 守护进程所在的核占用达到 153%（上限 200%）：所有评测容器的 stdio 中继，以及其他评测的 `docker commit/cp/rm`，都挤在这一个核上。
3. 开发负载在最坏情况下约使计时变慢 3%（约 1 分）。

据此采用的隔离策略：

- 指数传播 `grade_isolation = quiet`：评测期间不运行任何其他评测，也不运行任何开发；等待中的 quiet 请求会暂停新开发和新评测的启动。每份提交约 4 分钟。
- 优化器 `grade_isolation = grade_pool`：一次只运行一个评测，允许开发在其他 L3 域并行。得分只看逐例时限内是否成功，开发负载造成的约 3% 计时偏差只可能改变紧贴时限的用例。baseline 与候选在同一策略下评测。
