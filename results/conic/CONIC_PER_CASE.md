# 锥优化题：逐例评测明细（给出题人）

本包汇总锥优化题（conic-solver 0.3.0 / success-v2）在本机的完整评测数据，供讨论如何修改题目。内容包括参考实现和各模型提交在全部 650 个私有实例上的逐例、逐次运行记录，以及各模型提交的源码。总体结果和方法见 `report/CONIC_FULL.md`。

**本包含有私有实例的 ID、规模、时限和逐例结果，只供出题方使用，不要提供给参赛 agent。**

## 1. 包内文件

| 路径 | 内容 |

| `README.md` | 本说明 |

| `per_case/conic-per-case-summary.csv` | 宽表：每个实例一行，列出本机重标定时限下参考和各模型的结果 |

模型提交包括 gpt-6.1-sol、gpt-6-astra、hy4、claude-opus-5-5，均为协议 v6：一次尝试，2 小时，断网，原生 harness，最高推理设置。step-5-preview 在期限内没有冻结出有效提交，不包含在内。deepseek-v4-pro 和 minimax-m3.1-flash 的全集评测仍在进行，本包暂不包含。各实例的解文件（`solution.npz`）每个模型约 1.6 GB，没有放进包里，需要时可以另外提供。

## 2. 字段说明

`conic-per-case-runs.csv` 每行是一次求解运行：

| 字段 | 含义 |
| --- | --- |
| `case_id`、`group`、`n`、`m`、`nnz_P`、`nnz_A`、`cone_types` | 实例信息，取自原 manifest |
| `limit_original_s` | 题目包冻结的时限，按原机器标定 |
| `limit_recalibrated_s` | 按同一规则、用本机参考运行重新标定的时限 |
| `solver` | `reference` 为 Clarabel 0.11.1 参考提交，其余为模型名 |
| `run` | `original_limits`：原时限下的全集运行；`remeasure_2x_limit` / `remeasure_300s`：参考在原时限超时后的补测；`recalibrated_regrade`：模型在重标定时限下重评的实例 |
| `run_limit_s` | 这次运行实际使用的时限 |
| `repeat` | 第几次重复（每个实例 3 次，每次都是新进程） |
| `outcome`、`reason`、`status` | 原评测器给出的结果、原因（如 `solved_verified`、`time_limit`、`residual_tolerance_exceeded`、`unresolved`）和解的状态 |
| `elapsed_s`、`elapsed_over_limit` | 原评测器计的耗时（从进程启动到退出，含解释器启动和导入），以及它与时限的比值 |
| `residual_primal`、`residual_dual`、`gap_relative`、`certificate_margin` | 独立检查器计算的残差，容差 1e-8；不可行证书给出 `certificate_margin` |

`conic-per-case-summary.csv` 每行一个实例。每个求解器给出 `_solved`（重标定时限下是否解出）、`_slowest_s`（判定所用那轮运行中最慢一次的耗时）、`_failure_reasons`、`_deciding_run`；模型列另有 `_time_ratio_vs_reference`，即双方都解出时相对参考的耗时比。

判定规则与原题一致：三次重复都在时限内通过独立检查且状态一致，才算解出。

## 3. 对修改题目可能有用的观察

### 3.1 公开开发用例与私有评测集的时限分布不一致

| 时限 | 公开 dev（163 例） | 私有，原时限（650 例） | 私有，本机重标定 |
| --- | --- | --- | --- |
| 1 秒（下限） | 0 | 422 | 404 |
| 1–300 秒之间 | 0 | 90 | 109 |
| 300 秒（上限或参考失败） | 163 | 138 | 137 |

开发时 agent 看到的时限全部是 300 秒，而私有集 65% 的实例只有 1 秒。题目说明中还有 "Timing is diagnostic and has no separate score"，agent 很难意识到速度会决定大部分实例的成败。

### 3.2 1 秒下限主要在测进程启动开销

各求解器在 1 秒实例上三次中最快一次的中位耗时：参考 0.28 秒，hy4 0.39，Opus 0.45，astra 0.47，sol 0.53。这些实例规模都很小，耗时以 Python 启动、导入和数据读写为主。

模型在 1 秒实例上大量以 1.0–1.1 秒刚好超时：sol 67 例、astra 78、hy4 98、Opus 108，参考是 0。机器越慢，固定 1 秒留给求解的余量越少。

### 3.3 1.2 倍余量与机器差异

- 原时限 = 原机器参考三次中最慢一次 × 1.2。在时限介于 1–300 秒的实例上，本机参考比原机器慢：中位数 1.27 倍，90 分位 2.3 倍；有 7 个实例慢约 2.7–3.1 倍。因此按原时限，参考在本机只能解出 447 例。
- 本机重标定（同一规则）后，参考解出 513 例，与原机器的数字相同。
- 原时限下参考解出、时限大于 1 秒的实例里，参考最慢一次占时限的比例中位数为 0.92，90 分位为 0.98。也就是说，在原机器之外的环境里，时限几乎没有余量。

### 3.4 参考自身失败的 137 个实例

参考在 137 个实例上无论给多少时间都失败，这些实例按规则给 300 秒：

- **128 个是 `residual_tolerance_exceeded`**：Clarabel 认为已经解出，但独立检查器在 1e-8 容差下判为不合格。超标的主要是 dual 残差。384 次运行中，最大残差与容差之比的中位数约为 21，有 147 次在 10 倍以内。Clarabel 自己的停止容差也是 1e-8，但它的残差定义与检查器不同。
- 另有 6 个 `unresolved`，以及时间、内存、无效结果各 1 个。

这些实例给了模型"超过参考"的空间：sol 在 300 秒档解出 105 例，astra 55 例，hy4 43 例，Opus 31 例。

### 3.5 分档结果（本机重标定时限）

| 求解器 | 1 秒档（404） | 1–300 秒档（109） | 300 秒档（137） | 合计 |
| --- | --- | --- | --- | --- |
| 参考 | 404 | 109 | 0 | 513 |
| gpt-6.1-sol | 333 | 29 | 105 | 467 |
| gpt-6-astra | 322 | 27 | 55 | 404 |
| hy4 | 274 | 22 | 43 | 339 |
| claude-opus-5-5 | 293 | 10 | 31 | 334 |

- 1–300 秒档里，模型的失败几乎都是超时：sol 78 例、astra 81、hy4 76、Opus 97。
- 但在双方都解出的这档实例上，模型的耗时中位数约为参考的 0.5 倍。模型输掉的是它们求解得明显更慢的那部分实例，在能解出的实例上往往比参考快。
- 300 秒档里，模型的失败主要是 `unresolved`：没有给出合格的解或不可行证书。

## 4. 可以考虑的修改方向（供出题人判断）

- 公开开发用例的时限分布与私有集保持一致（包含 1 秒级实例），并在说明中写明计时包含进程启动和导入。
- 1 秒下限改为与启动开销相适应的值，例如"本机参考的启动时间 + 固定余量"，或者把启动时间从计时中扣除。
- 把余量从 1.2 倍放宽到 2–3 倍，降低评测机器之间的差异和运行噪声的影响；评测时在评测机器上重跑参考来标定时限。
- 检查 1e-8 残差容差与参考求解器停止条件之间的一致性：目前约 20% 的实例参考本身就无法通过。
- 计分方面，"解出数低于参考的 90% 即 0 分"会把大部分模型压到 0，可以同时报告配对计时，或者让映射在低端更平缓。

## 5. 数据来源

- 评测服务器：KVM 虚拟机，AMD EPYC 7K62（Zen 2），16 核 × 2 SMT，62 GiB 内存。
- 评测方式：每个评测容器 1 个 CPU、8 GiB 内存、无网络。4 个评测 slot 各占一个 L3 域。参考和模型使用相同的分片和相同的 slot 映射。
- 生成方式：本包由 `scripts/conic-per-case-export.py` 从评测记录生成，原始记录在仓库 `store*/` 目录下。
