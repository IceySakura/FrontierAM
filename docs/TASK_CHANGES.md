# 增加题目与修改题目

出题人负责题目本身（题面、数据、评测器、参照）；维护者负责接入评测系统、在本机重测参照、检查计分，然后开放给模型。

## 提交方式

- **有内部仓库权限**：在内部仓库开分支、提合并请求。私有数据可以放进去；单个文件超过 50 MB 用 Git LFS。
- **只有 GitHub 权限**：在 GitHub 提 PR，只含公开部分（题面、samples、public、评测器、参照、生成脚本）。私有数据单独交给维护者。
- 私有数据（private 用例、参考答案、生成种子）不要出现在 GitHub、issue 或聊天记录里。

## 增加题目

在 `tasks/<题目>/` 下按现有题目的结构建目录（英文小写、连字符），交付以下内容：

| 内容 | 位置 | 要求 |
| --- | --- | --- |
| 题面 | `versions/v1/statement.md` | 目标、输入输出格式、资源限制（CPU、内存、时限）、评分公式、允许与禁止的做法 |
| 数据 | `versions/v1/data/samples/`、`public/`、`private/` | samples 给模型看，从 public 中选几例；public 不给模型，只用于迭代反馈；private 用于最终评分。附生成脚本或来源说明 |
| 评测器 | `versions/v1/grader/` | 输入一个提交目录，输出每例的状态（通过 / 答错 / 超时 / 崩溃）、精度、用时，以及总的原始指标；同一提交评两次结果应一致 |
| 运行环境 | `versions/v1/Dockerfile` | amd64，可离线构建；提交在其中构建和运行 |
| 参照实现 | `references/r1/` | 按 `results/BASELINE_POLICY.md` 选本机实测最强的人类方法（开源优先）；只在 public 上调参，然后冻结 |
| 得分映射 | `meta.json` 与题面 | 参照 = 50，可达的最好结果 = 100，无效提交 = 0；指标跨几个数量级时用对数刻度 |
| 反馈分类（可选） | `meta.json` 的 `v63_data.groups` | 用例明显分成本质不同的几类时才分，类别要能从题面看出来；否则只报总计 |
| 题目说明 | `meta.json` | 英文名、一句话说明、背景、评测依据、baseline；README 由它生成 |

维护者接入：

1. 封存数据与评测器，构建镜像，题目在评测系统中自动出现（`tasks/*/versions/*/task.json`）。
2. 在本机评测槽上重跑参照，确定计分锚点。
3. 检查：时限对参照至少留 25% 余量；分数不会饱和（远超参照的结果仍能区分）；同一提交两次评分一致。
4. 生成 README 与看板（`scripts/site/build_task_pages.py`、`scripts/site/build_dashboard.py`），开放给模型。

## 检查或修改现有题目

1. 从 `tasks/<题目>/README.md` 读起：版本、数据划分、评测依据、参照、各模型的解法与成绩。
2. 只改说明文字、不影响评分（错别字、补充解释）：直接改原文件。
3. 影响评分的改动（题面规则、数据、评测器、时限、得分映射）：新建 `versions/<下一版>/`，在 `meta.json` 的 `versions` 中写明改了什么、为什么改。旧版本和旧成绩保留不动；新版本由维护者重跑参照和模型。
4. 参照由出题人提供或深度参与，不声称是 SOTA，也不因被模型超过而升级。任一格子 ≥ 80 分或高分段分不开时，维护者通知出题人；出题人决定是否修改参照（新版本的 `references/r<k>/`），旧成绩仍对应原参照（`results/BASELINE_POLICY.md`）。
5. 每轮评分后，维护者在 `meta.json` 的 `insights` 中更新这道题的“结果解读”（README 一节、看板“结果解读”页、`results/INSIGHTS.md`）。标“需出题人处理”的条目由出题人决定怎么改，按第 3、4 条出新版本。
6. 发现问题但不打算自己改：开 issue（不含私有数据），写明题目、版本和现象。
