# A5B BigRun Bad Pattern 假阳 / 假阴分析

生成日期：2026-10-01

最后核验：2026-10-01 19:45 CST

## 1. 文档目的

本文分析 0930 A5B BigRun 启用 `bad-pattern-v1` 后的真实轨迹命中情况，回答以下问题：

1. 哪些规则的命中基本可信；
2. 哪些规则存在假阳（false positive）；
3. 哪些规则存在假阴（false negative）；
4. 假阳 / 假阴是否真正影响 reward；
5. 应如何修改 detector、消息转换链路和策略配置；
6. 需要补哪些回归测试。

这里的“假阳”指正常行为被判为 bad pattern；“假阴”指真实 bad pattern 没有被在线 detector
捕获。

本文不把所有“可疑”都直接定性为 bug。结论按证据强度分为：

- **确定**：有运行时 receipt、结构化参数或完整轨迹可以交叉验证；
- **高概率**：现象和代码逻辑一致，但缺少运行时权威字段；
- **风险**：存在理论漏检/误判路径，尚未在本批轨迹中完整复现。

- tool_call_id 在部分 HY DSL 中需要重建；

- 离线还原器会根据 `<tool_use_error>` 补 `is_error=true`，而在线消息链路可能没有该字段。

因此本文优先采用“在线 metrics + 运行时 receipt + 离线重扫”三方一致的证据。

2. `tool_call_args_invalid`：Frontend `AskUserQuestion.multiSelect`；

1. Code topic 的 `edit_call_failure`；
2. Code topic 的 `edit_call_never_recovered`；
3. 部分运行时 `No such tool available`；
4. 部分运行时 `Input validation error`。

## 7. `final_turn_language`

### 7.1 真阳

Dreaming 中大量轨迹是中文任务、英文最终回复：

```text
Done. Final state...
Implemented the three stubs...
All tests pass...
```

这些发生在正常 `ENV_DONE` 的完整最终回复，属于真实语言不一致。

最近数据：

| 实验 | Dreaming 命中 | ENV_DONE | TRUNCATION | 实际被扣分 |
| --- | ---: | ---: | ---: | ---: |
| Frontend | 81 | 68 | 13 | 50 |
| 非 Frontend | 64 | 45 | 19 | 42 |

非截断部分大多是真阳，应保留。

### 7.2 确定假阳：截断末轮

最近 204 条语言命中中，至少 82 条发生在 `TRUNCATION`：

- Frontend WebJudger：33 条全部截断；
- Stackoverflow：大量截断；
- Dreaming：32 条截断。

Frontend 的真实示例：

```text
<tool_calls:6124c78e>
  <tool_call:...>Write
  <arg_value:...>大段 JS / HTML / Python...
```

这不是完成后的自然语言答复，而是被截断的工具调用。拉丁字母、代码和 DSL 标签占比高，被误判为“英文回复”。

Frontend WebJudger 的 33 条截断命中中，22 条所在轨迹实际被扣 0.3。这是当前最明确、
数量最大的假阳 reward 影响。

### 7.3 修复建议

实施状态（2026-10-01）：

- 已实现第 1 项：截断轨迹的全局最后 assistant finding 降为 nonissue evidence；
- 已覆盖 `termination_reason` 和 message `finish_reason=length` 两条截断信号；
- 已吸收 `db25d7d978` 的完整 raw HY tool-call-only final suppression，覆盖第 2～3 项；
- 自然语言密度判断仍是待办，不在本次修复范围内。

满足以下任一条件时跳过 `final_turn_language`：

1. `termination_reason in {TRUNCATION, OUTPUT_LENGTH_EXCEEDED}` 且命中最后一轮；
2. 最后一轮只有 tool call，无自然语言正文；
3. 正文主体为 HY tool-call DSL；
4. 自然语言字符数低于最小阈值。

必须补测试：

- 中文任务 + 截断 Write/Edit tool call；
- 中文任务 + 完整英文 final；
- 中文任务 + 英文代码块但中文 final；
- 中文任务 + tool-call-only assistant。

## 8. `tool_call_args_invalid`

### 8.1 MCP：真阳为主

运行时 receipt 验证：

| 实验 | runtime 明确拒绝 | runtime 接受 |
| --- | ---: | ---: |
| Frontend | 约 222 | 约 7 |
| 非 Frontend | 约 261 | 约 17 |

真阳比例约 94%～97%。

真实错误：

```text
missing required property
enum violation
type mismatch
value exceeds maximum
additional properties not allowed
```

例如：

```text
tool: mcp__oa_mcp_server_dev__get_shop_pict_sales_list
missing: $.dateType
runtime: Input validation error: 'dateType' is a required property
```

### 8.2 Frontend `AskUserQuestion` 假阳

Frontend 中 detector 报：

```text
missing $.questions[i].multiSelect
```

但 runtime 返回：

```text
User has answered your questions...
```

最近调用级统计：

- 16 次 `missing_required` 被 runtime 接受；
- 其中 14 次为 `AskUserQuestion`；
- 另有 2 次 Edit schema finding 被 runtime 接受；
- 其余 type/enum/constraint 大多被 runtime 拒绝。

根因是 advertised schema 把 `multiSelect` 标为 required，但运行时有默认值或允许省略。

修复顺序：

1. 修正 `AskUserQuestion` schema；
2. detector 看到配对 tool response 明确成功时，将 finding 标为 nonissue；
3. 记录 `schema_violation_but_runtime_accepted` 监控指标。

### 8.3 参数错误假阴

轨迹中含运行时 `Input validation error`，但在线规则未命中：

| 实验 | 有 runtime validation receipt | detector 命中 | 未命中 |
| --- | ---: | ---: | ---: |
| Frontend | 225 | 137 | 88 |
| 非 Frontend | 352 | 196 | 156 |

这是未命中的上界，不代表全部是 detector bug：

- 一部分错误来自 Bash 内部手工调 MCP，不属于结构化 tool-call detector；
- 一部分运行时 schema 与 advertised schema 不一致；
- 一部分并行 tool call/result 配对失败。

确认的结构化漏检例子：

```text
tool_call: mcp__llm_wiki__wiki_ingest
runtime: Additional properties are not allowed ('topic' was unexpected)
detector: 未命中
```

建议新增 receipt 驱动的补充路径：

```text
Input validation error
MCP -32602 invalid arguments
schema validation failed
```

按 `tool_call_id` 回连调用，并与静态 schema detector 取并集。

## 9. `tool_call_hallucination`

### 9.1 真阳

在线命中的 MCP hallucination 基本同时满足：

1. tool 不在完整 registry；
2. runtime 返回：

```text
No such tool available: <tool_name>
```

典型例子：

```text
mcp__iwiki_cli__getInlineComment
mcp__iwiki_cli__getDocumentTags
mcp__pixso_mcp__set_selections
mcp__cysm_operation_data__query_bdcs_profit_overview_data
```

主要成因：

- server 前缀写错；
- 把另一个 MCP server 的工具名移植过来；
- 猜了相似但不存在的工具；
- 大小写 / 分隔符错误；
- tool name 中混入 HY DSL 残片。

### 9.2 假阴

运行时 receipt 覆盖：

| 实验 | 含 `No such tool available` | detector 命中 | 未命中 |
| --- | ---: | ---: | ---: |
| Frontend | 187 | 169 | 18 |
| 非 Frontend | 298 | 222 | 76 |

约 19% 的 receipt 轨迹没有在线 hallucination hit。确认漏检样本：

```text
mcp__insuite_erp__erp_get_vendor_with_stock
mcp__h3yun_connector__h3yun_todo_count
mcp__query_pmc_projects
mcp__efficiency_platform__list_projects
```

高概率原因：

- 并行 tool call/result 的 ID 配对不完整；
- 动态 registry 的 completeness 判断；
- malformed tool name；
- tool result 缺准确 `tool_call_id`。

修复建议：

1. 把运行时 `No such tool available: name` 作为强证据；
2. 从 receipt 提取 name 回连最近同名调用；
3. 静态 registry 完整时继续做现有检查；
4. 将“静态未定义”和“运行时明确不存在”分别计数。

## 10. Edit 规则

### 10.1 `edit_noop_call`

规则只比较：

```text
old_string == new_string
```

最近在线命中 208 条，证据清晰，基本是真阳。

典型 runtime 也会返回：

```text
No changes to make: old_string and new_string are exactly the same.
```

该规则不依赖 tool result 的错误状态，所以 Frontend 和 Code topic 都能正常捕获。

### 10.2 `edit_call_failure` / `edit_call_never_recovered` 假阴

在线：

| topic | failure | never recovered |
| --- | ---: | ---: |
| Frontend WebJudger | 55 | 8 |
| SWE / Terminal / Dreaming / RepoQA / Setup / Stackoverflow | 0 | 0 |

离线重扫同一批 Code 轨迹：

| topic | 连续 Edit failure |
| --- | ---: |
| SWE | 66 |
| Dreaming | 31 |
| Stackoverflow | 17 |
| RepoQA | 12 |
| Terminal | 11 |
| Setup | 2 |

真实 receipt：

```xml
<tool_use_error>
String to replace not found in file.
</tool_use_error>
```

规则在文本正则前会调用 `is_error_result()`：

```python
bool(message.get('is_error'))
or inferred_outcome == 'failure'
or exit_code != 0
or status in {'error', 'failed', 'failure'}
or body starts with Error/Exception/Traceback
```

Code topic 在线 `quality_messages` 丢失了 `is_error/status/inferred_outcome/exit_code`。正文以
`<tool_use_error>` 开头，不满足现有 fallback，因此规则直接跳过。

Frontend 路径保留了 `is_error`，所以可以命中。

### 10.3 对延迟扣分的影响

Edit failure 本应折叠进：

```text
legacy_str_replace_old_eq_new
```

再由 trainer 在满分时扣 0.1。

实际在线 breakdown：

- Frontend：failure / never-recovered 能进入 legacy；
- 所有 Code topic：legacy 中 failure / never-recovered 仍为 0；
- 只有 no-op 被扣。

因此这是 reward 级假阴，不只是监控漏报。

### 10.4 修复建议

实施状态（2026-10-01）：

- 已完成最小安全修复：`is_error_result()` 识别正文开头的 `<tool_use_error>`；
- 已增加 detector 与 legacy deferred 回归测试；
- 已吸收 `db25d7d978` 的 Anthropic block normalization：
  `tool_use/tool_result` 转为 OpenAI tool call/result，并保留错误元数据；
- 已在 Harbor `quality_messages` 进入 detector 前统一归一化；
- 真实训练重启后的在线指标验证仍待进行。

根本修复：

- Anthropic ToolResult → OpenAI tool message → ChatTracker 全链路保留：
  `is_error`、`status`、`inferred_outcome`、`exit_code`。

安全 fallback：

```python
re.match(r'^\s*<tool_use_error>', body, re.I)
```

`<tool_use_error>` 是 harness 的协议标签，比任意包含 `error` 的文本安全。

## 11. `repetition_tool_call`

### 11.1 已修好的部分

当前规则：

- `TaskOutput` + `retrieval_status=timeout` 不报；
- 英文 polling 状态允许最多 3 次重复；
- 第 4 次以上才报一次。

本批命中中没有 `TaskOutput timeout` 假阳，说明该修复生效。

### 11.2 真阳

多数命中是原调用失败后原样重试：

```text
Edit: String to replace not found
Bash: ModuleNotFoundError
MCP: missing required property
```

这类重复调用参数和结果都完全一致，没有修正行为，属于真阳。

### 11.3 中文 polling 假阳

当前 polling 正则只识别英文：

```text
queued / running / pending / processing /
temporarily_unavailable / throttled ...
```

真实返回：

```text
【生成中】语料生成任务尚未完成，请间隔约 30 秒后再次调用
get_generation_status 查询
```

这被分类为普通重复调用，并可能扣 0.3。

最近确认：

- `get_generation_status`
- `stock_analyze_result`
- Humanlaya 临时不可用 fetch

建议加入：

```text
生成中、排队中、处理中、尚未完成、等待生成、
任务运行中、请稍后、暂不可用
```

并允许 3～5 次重复状态查询。

另外，重复 `Read` 同一截图可能是视觉复查，不一定等同于无意义重复，建议对图像 Read 单独监控。

## 12. `reasoning_selftalk_flood`

最近仅 2 条，两条均为假阳：

1. Frontend：思维链中绘制 ASCII 像素字形；
2. WideSearch：逐行枚举比赛胜负和数字。

规则按 200 字符窗口中的换行和自述词计数，把结构化草稿误判成空转。

建议排除：

- ASCII art；
- 以数字/短表格行为主的窗口；
- glyph / bitmap / matrix 上下文。

修复前建议 `penalize=false`。

## 13. HY 协议泄漏

### 13.1 `think_protocol_leak_hy`

真实例子：

```text
正文中出现 </think:6124c78e>
```

说明 reasoning parser 未消费标签，属于真阳。

### 13.2 `tool_call_protocol_leak_hy`

真实例子：

```text
assistant content 中原样出现：
<tool_calls:...><tool_call:...>Write...
```

说明 tool parser 未把 DSL 转成结构化 tool_calls。

当前版本已对“截断最后一轮中的不完整协议片段”做 suppression，旧版大量截断假阳已明显下降。

仍需关注：

- 截断中出现完整、平衡的协议块时不会被 suppression；
- 中间轮协议泄漏仍然会报；
- 有些 `ENV_DONE` 轨迹最终 assistant 仍是原始 tool-call DSL，这是真 parser failure。

总体上该规则真阳为主。

## 14. all-family 规则

最近命中 32 条，当前 `penalize=false`。

仍存在混合情况：

### 真问题

- `</content></invoke>` 被写入 HTML/Python 文件；
- assistant reasoning 承认“我把 closing tag 写进文件了”；
- tool argument 尾部残留协议 closing tag。

### 可疑/假阳

- reasoning 中引用协议标签讨论；
- C++ 泛型或文档 `<parameter>`；
- 文件内容包含示例标签；
- 数学/文本上下文附近的泛化 XML pattern。

结论：继续 monitor-only，不建议开启扣分。

## 15. `mojibake` / `punct_flood`

本批 18,485 条有效轨迹均为 0 命中。

目前没有证据说明规则失效；也没有发现明显乱码/符号刷屏漏检。可继续启用。

## 16. Reward 影响归因

736 条固定扣分中：

- 约 70% 来自 MCP hallucination / args invalid；
- 约 13% 来自 Dreaming language；
- 剩余来自协议泄漏、重复调用、Frontend language/schema 等。

MCP 的真阳率高，但扣分覆盖面很大：

| 实验 | MCP 有效轨迹 | 被固定扣分 |
| --- | ---: | ---: |
| Frontend | 554 | 38.45% |
| 非 Frontend | 988 | 30.47% |

即使判断正确，0.3 的统一扣分也可能过强。一次可恢复的早期工具错误会让整条成功轨迹奖励降低 0.3。

建议对 MCP 单独使用 0.1～0.2，或仅在同类错误重复 2 次以上时扣 0.3。

## 17. 修复优先级

### P0：直接影响 reward

1. `final_turn_language` 跳过截断末轮和 tool-call-only 轮；
2. 修复 Code tool result 的 `is_error` 保留；
3. `is_error_result()` 识别锚定的 `<tool_use_error>`；
4. 修正 `AskUserQuestion.multiSelect` schema。

### P1：提升覆盖率

## 18. 建议回归测试

### 语言

- 中文 prompt + 完整英文 final → hit；
- 中文 prompt + 截断 tool call → no hit；
- 中文 prompt + 英文代码块 + 中文 final → no hit；
- tool-call-only final → no hit。

### 参数

- schema missing required + runtime reject → hit；
- schema missing optional + runtime success → nonissue；
- parallel calls 的 validation receipt 正确绑定 call ID。

### hallucination

- 完整 registry 中不存在 + runtime No such → hit；
- 动态暂不可用但已声明 → nonissue/monitor；
- malformed name 能回连原始调用。

### Edit

- `<tool_use_error>String to replace not found` 连续两次 → failure；
- 后续成功 → 不命中 never-recovered；
- 无后续成功 → never-recovered；
- old==new → no-op；
- Frontend 与 Code 转换路径结果一致。

### repetition

- TaskOutput timeout → no hit；
- `queued/running/生成中` 前 3 次 → no hit；
- 长期不变超过阈值 → hit；
- 同参数失败后原样重试 → hit。

### protocol

- 截断最后一轮不完整标签 → suppressed；
- 中间轮完整泄漏 → hit；
- fenced 示例 / 文件合法内容 → all-family nonissue；
- 标签真正写入文件尾部 → monitor finding。

## 19. 最终建议

当前策略可以继续训练，但不建议直接照现状推广到更大规模：

1. 先修 P0 四项；
2. MCP penalty 降至 0.1～0.2 或增加重复次数门槛；
3. all-family 保持只监控；
4. 修复后用同一批轨迹离线 replay，对比：
   - 旧/新命中差异；
   - reward 反事实；
   - 每 topic 扣分率；
   - 假阳/假阴证据闭环。

最重要的三处是：

```text
截断末轮语言假阳
Code Edit failure 假阴
MCP runtime receipt 漏检
```

这三处分别代表了当前策略的主要误扣、漏扣和覆盖率缺口。
